# Vertex: the My Learning page, wired to learner progress

## Goal

Build the My Learning page and connect the nav link that currently goes
nowhere. It shows the courses this learner has actually started, how far
through each one they are, and a way back into the lesson they stopped in.

## Decisions and assumptions

**There is no design reference for this page.** CLAUDE.md section 3 says the
user supplies the design and I reproduce it; none was given here. So this page
invents no visual language: it is the `/courses` page shell — same breadcrumb,
heading scale, lede and spacing — filled with `CourseGrid` and `ProgressBar`,
both already in the project. If a reference turns up later, this is meant to be
restyled to it, not defended.

**The route is `/my-learning`**, matching the nav label.

**Read-only, and no new write path.** Section 7 lists My Learning among the
presentational surfaces, allowed to read existing progress for display. It
records nothing and adds no route.

**One query, not one per course.** A new `MY_LEARNING_QUERY` filters
`progress` by user id and joins the course through the reference, so the page
is a single read. Ordered by `updatedAt desc`, so the most recent work is
first — the ordering the page is actually about.

**A progress record whose course is gone is dropped**, not rendered as an
empty card. References are weak in effect here: an author deleting a course
should not break a learner's page.

**Three sections, derived not stored**: one "Continue learning" card for the
most recently touched unfinished course, then "In progress", then "Completed".
A course is complete when its percentage reaches 100, computed with the same
`percentComplete` the rest of the app uses, so the page cannot disagree with
the course page about how far along someone is.

**Signed out is a first-class state**, not a redirect. Browsing is public
(section 7), so the page explains what My Learning is and links to `/sign-in`
and `/courses`. Gating it in middleware would be the wrong tool: nothing here
is sensitive until there is a user, and there is no user.

**`robots: noindex`.** Every visitor sees different content and a crawler sees
the signed-out state; there is nothing to index.

**One PostHog event**, `my_learning_resumed`, on the Continue card's CTA. The
existing `course_card_clicked` already covers the grid, and section 7's list of
engagement moments does not ask for a page-view event here.

## Requirements

1. `/my-learning` renders, signed in, a page listing every course the learner
   has started, most recently worked on first.
2. A "Continue learning" card at the top for the most recent unfinished course:
   cover, title, percentage, `ProgressBar`, and a CTA to
   `lessonHref(resumeTarget(...))` — the lesson they stopped in, at the second
   they stopped at. Absent when every started course is finished.
3. An "In progress" grid (percentage 1–99) and a "Completed" grid (100),
   each rendered through `CourseGrid` with its per-card bar. A section with no
   courses is not rendered at all.
4. Signed in with no progress: an empty state that links to `/courses`.
5. Signed out: an explanatory state linking to `/sign-in` and `/courses`. No
   crash, no 401, no request for progress.
6. The nav "My Learning" link points at `/my-learning` and behaves exactly like
   the "Courses" link beside it.
7. Responsive to mobile, per section 3: the grids collapse to one column and
   the Continue card stacks.
8. Counts shown on the page are derived from the fetched data — never stored,
   never guessed.

## Security considerations

- The page reads progress scoped by the Clerk user id taken from `auth()` on
  the server. No user id is ever accepted from the URL or a query param, so
  there is no way to ask for someone else's My Learning.
- The read is uncached (`fresh`), so Next's Data Cache cannot serve one
  learner's page to another. The route therefore renders dynamically, which is
  correct for per-user content.
- Reads go through the existing `server-only` Sanity client with the read
  token. No write client, no write token, and nothing new reaches the browser.
- Progress documents are outside the Context MCP's type allowlist, so nothing
  here widens what the search agent can see.

## Acceptance criteria

- Clicking "My Learning" in the nav lands on `/my-learning`.
- A course watched part-way appears under "In progress" with a real percentage,
  and the Continue card resumes it at the right lesson and second.
- Completing every lesson in a course moves it from "In progress" to
  "Completed", and the Continue card falls through to the next unfinished
  course.
- A learner with no progress sees the empty state, not an empty page.
- Signed out, the page explains itself and offers sign-in.
- The percentage on a card matches the one on that course's own page.

## Checks to run

In `web/`: `npx tsc --noEmit`, `npm run lint`, `npm run build` (a new route and
a changed server module). In `studio/`: `npm run typegen` after the query is
added, so the generated result type exists. No schema change, so no schema
deploy.

## Manual test steps

1. `npm run dev` in `web/`, signed in.
2. Click "My Learning" in the nav — it goes to `/my-learning`.
3. With no progress yet: the empty state offers the catalog.
4. Watch part of a lesson, return. The course appears under "In progress" with
   a percentage, and the Continue card names that lesson.
5. Click the Continue CTA — it opens that lesson at the saved second.
6. Complete every lesson in a course; it moves to "Completed" and the Continue
   card advances to another course.
7. Compare the percentage on the card with the bar on that course's own page —
   they agree.
8. Resize to mobile width: grids are single-column, the Continue card stacks,
   nothing overflows horizontally.
9. Sign out and revisit `/my-learning`: the explanatory state renders, with no
   console errors and no progress request in the network tab.
